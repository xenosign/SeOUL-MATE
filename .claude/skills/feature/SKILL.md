# /feature — 기능 개발 파이프라인

대상 기능: **$ARGUMENTS**

너(메인 세션)는 팀장이다. 아래 순서대로 `.claude/agents/`의 에이전트를 호출하고, 단계 사이의 결과를 다음 에이전트에게 넘긴다. 에이전트끼리는 서로를 호출할 수 없으므로 전달은 네가 한다. 각 단계를 시작할 때 사용자에게 한 줄로 알린다.

`$ARGUMENTS`가 비어 있으면 어떤 기능을 만들지 묻고 멈춘다.

## 1단계. 기획 (biz 팀)

1. **biz-product-planner**에게 스펙 작성을 맡긴다 → `docs/specs/<기능명>.md`.
   - 이미 같은 기능의 스펙이 있으면 새로 쓰지 말고 그 파일을 갱신하게 한다.
2. 스펙의 "안전·정책 고려"에 개인정보 노출, 사용자 간 상호작용, 만남, 금전, 신고/차단과 관련된 내용이 있으면 **biz-trust-safety**에게 `docs/policy/review-<기능명>.md` 검토를 맡긴다. 지적 사항은 planner에게 다시 넘겨 스펙에 반영한다.
3. 사용자 이해가 부족해서 결정하기 어려운 열린 질문이 있으면 **biz-user-researcher**를 선택적으로 호출한다.

## 2단계. 스펙 승인 — 반드시 멈춘다

스펙 요약(목표, 수용 기준, 데이터·권한 변경, 범위 밖)과 열린 질문을 사용자에게 보여주고 **승인을 받을 때까지 구현을 시작하지 않는다.** 사용자가 수정을 요청하면 1단계로 돌아간다. 승인되면 스펙의 상태를 "확정"으로 바꾼다.

## 3단계. 구현 (dev 팀 + 메인 세션)

1. 이 버전의 Next.js API를 확신할 수 없는 부분이 있으면 먼저 **dev-next16-docs**에게 묻는다.
2. 스펙에 DB 변경이 있으면 **dev-supabase-schema**가 새 마이그레이션, `src/lib/types.ts`, README를 처리하게 한다.
3. 화면, Server Actions, 컴포넌트는 메인 세션이 스펙의 수용 기준에 맞춰 직접 구현한다. 기존 코드 스타일을 따르고, 새 UI 문구는 `src/i18n/dictionaries/en.ts`에 키로 추가한다.

## 4단계. 다국어

**dev-i18n-sync**에게 ko/ja/zh 사전 동기화, 하드코딩 문자열 정리, 번역 품질 점검을 맡긴다.

## 5단계. 보안 리뷰

**dev-security-reviewer**에게 이번 변경(마이그레이션 포함)의 리뷰를 맡긴다. Critical/High 발견 사항은 고치고 다시 리뷰받는다. Medium 이하는 고칠지 사용자에게 보고한다.

## 6단계. 검증

**dev-verifier**로 lint, 타입 검사, 빌드, 스모크 테스트를 돌린다. 실패하면 고치고 다시 돌린다.

## 7단계. 보고

- 스펙의 수용 기준 체크리스트: 충족 / 미충족 / 수동 확인 필요.
- 변경 파일 목록, 새 마이그레이션(사용자가 Supabase에 직접 적용해야 함).
- 남은 보안 지적, 원어민 검수가 필요한 번역, 로그인 흐름처럼 수동으로 확인할 항목.

커밋, 푸시, PR, 원격 DB 적용은 사용자가 요청할 때만 한다.
