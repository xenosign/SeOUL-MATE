## 2. 역할별 제안

### 2.1 `dev-security-reviewer` — 보안·개인정보

**[Critical] 여행객이 요청의 status와 matched_guide_id를 마음대로 바꿀 수 있다 (알려진 문제, 확인함)**
- 위치: `supabase/migrations/0001_init.sql:161-164`
- 문제: `"travelers update own requests"` 정책은 `traveler_id = auth.uid()`만 확인한다. 컬럼 제한이나 상태 전이 검사가 없다.
- 악용 시나리오: 여행객이 브라우저에서 publishable key로 Supabase에 직접 `update guide_requests set status='completed', matched_guide_id='<아무 사용자 id>'`를 보낼 수 있다. 채팅한 적 없는 사용자가 "매칭된 가이드"가 되고, 그 사용자는 `0001_init.sql:152`의 select 조건(`matched_guide_id = auth.uid()`) 때문에 요청을 읽게 된다. 앞으로 후기·평점·완료 횟수 같은 신뢰 지표를 붙이면 그 지표도 조작할 수 있다.
- 앱 코드도 막지 않는다:
  - `src/app/requests/actions.ts:94-103` `acceptGuide`는 `guideId`가 이 요청에 채팅방을 연 가이드인지 확인하지 않는다.
  - `src/app/requests/actions.ts:111-123` `setRequestStatus`는 허용 전이 목록 없이 받은 `status`를 그대로 쓴다(예: `open → completed`). Server Action 인자는 클라이언트가 바꿔 보낼 수 있다고 보고 서버에서 검증해야 한다. `.bind`로 넘긴 인자가 암호화되는지는 문서 확인 필요(어느 쪽이든 DB 직접 호출 경로가 열려 있으므로 결론은 같다).
- 수정 방향: 새 마이그레이션 `0003_*`에서 기존 update 정책을 `drop`하고 `authenticated`의 `guide_requests` update 권한을 회수한다. 상태 변경은 `security definer set search_path = ''` RPC 두 개로만 하게 한다.
  - `accept_guide(p_request_id, p_guide_id)`: 호출자가 해당 요청의 여행객인지, status가 `open`인지, `chat_rooms`에 `(p_request_id, p_guide_id)` 방이 있는지 확인한다.
  - `set_request_status(p_request_id, p_status)`: 허용 전이만 통과시킨다. `open→cancelled`, `matched→completed`, `matched→open`(matched_guide_id null로), `cancelled→open`.
  - 현재 요청 본문을 고치는 UI가 없으므로 update 권한 회수의 부작용은 없다. 나중에 편집 기능이 생기면 내용 컬럼만 `grant update (...)`로 연다.
  - 대안: BEFORE UPDATE 트리거로 status·matched_guide_id 변경을 검사한다. 앱 코드 변경은 줄지만 규칙이 정책과 트리거에 흩어진다.

**[High] 로그인한 모든 사용자가 모든 프로필의 contact·instagram을 읽을 수 있다**
- 위치: `supabase/migrations/0001_init.sql:140-141` (`using (true)`), 컬럼 `0001_init.sql:17` `contact`, `0002_profiles_instagram.sql:5-7` `instagram`
- 문제: 화면은 "채팅 상대에게만 표시"라고 안내한다(`src/i18n/dictionaries/en.ts:62,65`). 하지만 DB는 로그인한 누구에게나 이 컬럼을 준다.
- 악용 시나리오: 구글 계정으로 가입만 하면 `select id, display_name, nationality, contact, instagram from profiles`로 전체 사용자의 카카오톡·WhatsApp·LINE ID와 인스타 계정을 한 번에 수집할 수 있다. 여행객(외국인, 여행 날짜·지역이 요청에 공개됨)을 노리는 스토킹·스팸에 쓰일 수 있다.
- 화면에서도 안내와 실제가 다르다:
  - `src/app/requests/[id]/page.tsx:20,181`: 열린 요청 상세에서 **채팅을 시작하지 않은** 모든 가이드에게 여행객의 instagram이 보인다.
  - `src/app/chats/[roomId]/page.tsx:33-34,74-78`: 가이드가 채팅방을 열기만 하면(매칭 전) 여행객의 contact가 보인다. 채팅방은 가이드가 일방적으로 만들 수 있다(`0001_init.sql:173-185`).
- 수정 방향: 민감 컬럼을 `profile_private(user_id pk, contact, instagram)` 같은 별도 테이블로 옮긴다. RLS는 본인 + 같은 채팅방 참여자(또는 매칭된 상대만, 비즈팀 결정)로 건다. 컬럼 권한 회수(`revoke select (contact)`)도 가능하다. 다만 `src/lib/auth.ts:16`처럼 본인 프로필을 읽는 쿼리와 `select *` 계열이 깨지므로 별도 테이블 쪽을 권한다. 기존 데이터 이관(백필)이 필요하다.

**[Medium] 로그인 페이지 open redirect**
- 위치: `src/app/login/page.tsx:9`
- 문제: 이미 로그인한 사용자가 `/login?next=https://evil.example`이나 `/login?next=//evil.example`로 들어오면 검증 없이 `redirect(next)`한다. `src/app/auth/callback/route.ts:10`에는 같은 사이트 경로 검사가 있지만 여기에는 없다.
- 악용 시나리오: 인스타 DM이나 커뮤니티에 "SeOUL MATE 로그인" 링크를 뿌려 피싱 사이트로 보낸다. 홍보를 시작하면 링크가 많이 돌기 때문에 위험이 커진다.
- 수정 방향: callback과 같은 `safeNext()` 헬퍼를 `src/lib/`에 두고 두 곳에서 쓴다. 노력 S.

**[Medium] 남용 방지 장치 없음**
- 요청 생성(`src/app/requests/actions.ts:12-58`), 채팅방 생성(`0001_init.sql:173-185`), 메시지(`0001_init.sql:191-193`)에 개수·속도 제한이 없다. 신고·차단 기능도 없다(`README.md:101`에 "다음에 해볼 만한 것"으로만 있음).
- 가이드 신원 확인 없이 누구나 `guide` 역할을 고를 수 있고 언제든 바꿀 수 있다(`src/app/profile/actions.ts:22-25`, 정책 `0001_init.sql:142-144`). 열린 요청 목록에는 여행객 이름·국적·날짜·지역이 나온다(`src/app/requests/page.tsx:7,51-57`).
- 수정 방향: 단기에는 DB 수준 개수 제한(예: 여행객당 open 요청 N개, 가이드당 하루 채팅방 N개), 중기에는 신고/차단 테이블과 운영자 처리 흐름. 정책 결정이 먼저 필요해 `biz-trust-safety`에 넘긴다.

**[Low] 기타**
- 매칭·완료·취소된 요청의 채팅방에서도 메시지를 계속 보낼 수 있다(`0001_init.sql:191-193`). 매칭되지 않은 가이드와의 대화가 남는 것은 의도일 수 있다.
- Realtime 채널 `room:${roomId}`가 private 채널이 아니다(`src/app/chats/[roomId]/chat-room.tsx:54`). postgres_changes는 RLS가 적용되지만 presence·typing broadcast는 방 id(UUID)를 아는 누구나 듣거나 위조할 수 있다(추정, Supabase Realtime Authorization 설정 확인 필요).
- DB 오류 원문을 사용자에게 그대로 보여 준다: `src/app/profile/actions.ts:54`, `src/app/requests/actions.ts:54`, `src/app/login/login-buttons.tsx:24`, `src/app/chats/[roomId]/chat-room.tsx:113`.
- 개인정보처리방침·이용약관 페이지와 회원 탈퇴 기능이 없다. 국적·연락처를 받으므로 출시 전에 처리방침 공개가 필요하다(법적 판단은 `biz-trust-safety`). 구글 OAuth 동의 화면을 프로덕션으로 전환할 때도 처리방침 URL을 요구할 수 있다(가설, 구글 콘솔에서 확인 필요).

### 2.3 `dev-next16-docs` — Next.js 16·홍보 지원

**현재 상태 (코드에서 확인)**
- `src/app/layout.tsx:19-22`: `generateMetadata`가 `title`과 `description`만 돌려준다. `metadataBase`, `openGraph`, `twitter`, `alternates`가 없다. 인스타 DM, 카카오톡, WhatsApp, LINE, Reddit, 페이스북 그룹에 링크를 올리면 미리보기 이미지가 없거나 기본값으로 나온다.
- `public/` 폴더가 없다. 아이콘은 `src/app/favicon.ico` 하나뿐이다. `opengraph-image`, `apple-icon`, `manifest`, `robots`, `sitemap` 파일이 모두 없다.
- 언어는 URL이 아니라 쿠키 → `Accept-Language` → 기본값 `en` 순으로 정한다(`src/i18n/server.ts:29-33`). 그래서:
  - 공유 미리보기 크롤러는 대부분 쿠키 없이 오므로 미리보기가 사실상 **항상 영어**다(가설, 크롤러의 Accept-Language에 따라 다름). 일본어·중국어 커뮤니티에 올려도 영어 카드가 뜬다.
  - 언어별 URL이 없어서 `hreflang`을 걸 수 없다. 검색엔진은 한 URL에 언어 하나만 색인한다.
- 랜딩 `/`은 로그인 없이 볼 수 있다(`src/lib/supabase/proxy.ts:4`에 보호 경로로 없음). 하지만 내용이 소개 3단계와 여행객 CTA 하나뿐이다(`src/app/page.tsx:8-31`). 가이드(자원봉사자) 모집 CTA는 커밋 `1af565a`에서 빠졌다.
- 유입 추적이 전혀 없다. 분석 도구도 없고 UTM 파라미터를 저장하지 않는다.

**인스타그램 인앱 브라우저 문제 (홍보 퍼널 차단 요인, 가설 — 실기기 확인 필요)**
- 인스타 프로필 링크, 스토리 링크, DM 링크는 기본적으로 인스타 앱 안의 웹뷰에서 열린다. 구글은 임베디드 웹뷰의 OAuth 로그인을 `403 disallowed_useragent`로 막는다.
- 로그인 수단은 구글·카카오 두 개뿐이다(`src/app/login/login-buttons.tsx:31-46`). 외국인 여행객 대부분은 카카오 계정이 없다. 따라서 **인스타로 들어온 외국인 대부분이 로그인 단계에서 막힐 가능성이 크다.** 카카오톡·LINE·페이스북 인앱 브라우저도 같다.
- 대응안:
  - (a) User-Agent로 인앱 브라우저(`Instagram`, `FBAN`/`FBAV`, `KAKAOTALK`, `Line` 등)를 감지한다. `/login`과 랜딩 CTA에 "외부 브라우저로 열기" 안내, 링크 복사 버튼, Android용 `intent://` 외부 브라우저 열기를 보여 준다. 노력 S.
  - (b) 웹뷰에서도 되는 이메일 OTP 로그인(Supabase Auth)을 추가한다. 노력 M. Supabase 기본 SMTP는 발송량 제한이 있어 실제 운영에는 SMTP 설정이 필요하다(무료 플랜 범위 확인 필요).
- 문서 확인 필요: 서버 컴포넌트에서 `headers()`로 UA 읽기. 기존 코드 `src/i18n/server.ts:32`에서 이미 `await headers()`를 쓰므로 패턴은 있다.

**문서 확인 필요 항목**
- `metadataBase`, 파일 기반 `opengraph-image.tsx`/`twitter-image.tsx`(`next/og`의 `ImageResponse`), `icon`/`apple-icon`, `manifest.ts`, `robots.ts`, `sitemap.ts`가 16.4.0에서 같은 이름·시그니처인지
- `src/proxy.ts:9-12` matcher가 위 메타데이터 라우트(`/opengraph-image`, `/robots.txt`, `/sitemap.xml`, `/manifest.webmanifest`)도 지나게 하는데, 문제가 없는지(세션 갱신 비용만 듦, 보호 경로는 아님)
- 언어 지정 링크(`/?lang=ja`)를 proxy에서 쿠키로 바꿔 같은 요청의 렌더링에 반영할 수 있는지. `src/lib/supabase/proxy.ts:19-20`의 `request.cookies.set` + `NextResponse.next({ request })` 패턴이 이 버전에서 요청 쿠키를 전달하는지

### 2.5 `dev-verifier` — 품질·빌드 가능성 (코드 읽기 기준, 실행 안 함)

- OAuth 로그인이라 요청 → 채팅 → 매칭 → 완료 흐름은 자동 검증할 수 없다. 1순위 보안 수정 후에는 사용자 수동 체크리스트가 필요하다.

### 2위. 인앱 브라우저 로그인 차단 대응 (C10)

- **선정 이유:** 홍보 채널(인스타 프로필·스토리·DM 링크, 카카오톡·LINE 공유)이 모두 인앱 웹뷰로 열린다. 그런데 외국인의 주 로그인 수단인 구글은 웹뷰에서 막힌다(가설, 실기기 확인 필요). 이 문제를 그대로 두면 다른 홍보 작업의 효과가 로그인 단계에서 사라진다. 노력 대비 효과가 가장 크다.
- **무엇을 바꾸나**
  - 1단계(S):
    - `src/app/login/page.tsx`에서 UA를 감지해 인앱 브라우저 여부를 `LoginButtons`에 전달

    - 랜딩(`src/app/page.tsx`) CTA 근처에 같은 안내
    - 사전 키 4개 언어 추가
  - 2단계(M, 비즈팀 결정 후): Supabase 이메일 OTP 로그인 추가(로그인 버튼 1개 + 코드 입력 폼). Supabase SMTP 설정은 사용자가 한다.
- **노력:** S(1단계) / M(2단계)
- **담당:** `dev-next16-docs`(`headers()` 사용, 문서 확인) → 메인 세션 구현 → `dev-i18n-sync`(안내 문구 4개 언어) → `dev-security-reviewer`(인증 흐름 변경이므로 2단계는 필수) → `dev-verifier`

- **비즈팀 확인:** 이메일 로그인 추가가 가입 장벽 해소에 필요한지, 인스타 프로필 링크가 어디로 갈지(랜딩 `/` 또는 별도 소개 페이지)

   - 개인정보처리방침·이용약관 문안(국적·연락처·채팅 수집 항목 포함), 회원 탈퇴·데이터 삭제 정책. 받으면 C5를 S로 바로 만든다.
   - 남용 대응 정책: 여행객당 열린 요청 수, 가이드당 하루 연락 수, 신고·차단 처리 주체, 가이드 신원 확인 여부(C4)
2. **`biz-growth-marketer`** → `docs/growth/`
   - 주력 채널과 언어 우선순위(인스타 영어 / ja·zh 커뮤니티 등). 3위의 `?lang=` 링크 포함 여부를 정한다.
   - 언어별 공유 카피(OG 제목·설명)와 이미지 안, 공식 인스타 계정 핸들
   - 채널별 UTM 규칙(`utm_source`/`utm_medium`/`utm_campaign` 값)과 보고 싶은 지표(방문 → 로그인 → 프로필 완료 → 요청 등록 / 가이드 첫 연락). 이것이 정해져야 C11(유입 추적)을 설계할 수 있다. 분석 도구 사용 시 처리방침 고지가 필요하다(1번과 연결).
3. **`biz-product-planner`** → `docs/specs/`
   - 가이드(자원봉사자) 모집 CTA를 랜딩에 다시 넣을지(커밋 `1af565a`에서 제거됨), 인스타 프로필 링크의 도착 페이지 구성(C12)
   - 이메일 OTP 로그인 추가 여부(2위 2단계). 구글·카카오 외 로그인 수단을 늘릴지 결정
   - 1위 보안 묶음 스펙 승인

- lint, `tsc`, 빌드, 스모크 테스트: `node_modules`가 없어 실행하지 않았다.
